## Files

| File | Role |
|---|---|
| `Dockerfile` | Two stages: Node 22 builds the Vite assets, then PHP 8.4-FPM Alpine + nginx + supervisord with `composer install --no-dev` |
| `docker/start.sh` | Container entrypoint — quick local work only, then `exec supervisord` |
| `docker/boot.sh` | One-off background work after the port is open: migrations, operator account, optional demo data |
| `docker/supervisord.conf` | php-fpm (10) → boot (15) → nginx (20) → scheduler (30) |
| `docker/nginx.conf.template` | Laravel front controller on `$PORT`, 1-year cache on `/build/*`, security headers |
| `docker/php-fpm.conf` | `clear_env = no` (the app needs the container's env), `pm.max_children = 5` for small instances |
| `render.yaml` | Render Blueprint: web service + managed Postgres |

## The image

Assets are built at image build time, not at boot — the container starts with `public/build` already in place, which is also what gives the service worker its version ([12](12-pwa-offline.md#service-worker)).

`composer install --no-dev` means **Faker and the dev seeders aren't in the image**; only the Faker-free seeders can run in production.

## What happens on boot

The split between `start.sh` and `boot.sh` exists because of a real failed deploy: migrations ran *before* nginx, the database was slow, no port opened in time and the host killed the deploy ("Port scan timeout reached, no open ports detected").

**`start.sh` — fast path, everything local:**

1. Default `PORT` to 10000.
2. Add the `base64:` prefix if the host generated a raw `APP_KEY`.
3. Use `RENDER_EXTERNAL_URL` as `APP_URL` when `APP_URL` isn't set.
4. Render the nginx config with `envsubst` for `$PORT`.
5. `config:cache`, `route:cache`, `view:cache`, `event:cache` — warnings only, never a hard exit.
6. `exec supervisord`.

**`boot.sh` — after the port is open:**

1. `php artisan migrate --force`, retried up to 20 times, 5 seconds apart, so a database that's still waking up is fine.
2. `php artisan app:ensure-super-admin` — creates or promotes the operator, and **leaves an existing password alone**.
3. If `SEED_DEMO_DATA=true`, load the demo shop (skipped when it already exists).

Nothing in `start.sh` exits on failure, so a broken environment variable produces a running site with a clear error instead of a container that never starts.

## Processes

supervisord runs php-fpm, nginx, the one-off boot script (`autorestart=false`) and `schedule:work` in one container. Logs go to stdout/stderr so the host collects them.

Health check: `GET /up`, Laravel's built-in route.

## Environment

| Variable | Notes |
|---|---|
| `APP_KEY` | Generated by the host; the `base64:` prefix is added for you |
| `APP_URL` | Defaults to the host's public URL. **Set it explicitly once you add a custom domain** — verification and password-reset links are built from it |
| `DB_*` | Postgres in production, SQLite for tests |
| `SUPER_ADMIN_EMAIL` / `_PASSWORD` / `_NAME` | The operator account ([10](10-platform.md)) |
| `SUPPORT_EMAIL` / `SUPPORT_PHONE` / `SUPPORT_MESSENGER_URL` | Shown when email fails ([01](01-authentication.md#when-email-fails)) |
| `MAIL_*`, `MAIL_TIMEOUT` | See below |
| `BILLING_GCASH_NUMBER`, `BILLING_BANK` | Shown on the owner's billing card ([09](09-team-settings.md#plan--billing)) |
| `SEED_DEMO_DATA` | `false` in production |

`config/iposa.php` collects the operator and support settings in one place.

## Running behind a proxy

`trustProxies(at: '*')` in `bootstrap/app.php`. Hosts like Render terminate HTTPS at their load balancer, so without this Laravel would generate `http://` URLs, break secure cookies and produce signed verification links that fail their signature check.

## Scheduled work

`routes/console.php` schedules `businesses:mark-overdue` daily at 00:05, run by the `schedule:work` process — no separate cron service to pay for. It moves trials and subscriptions past their due date to `past_due` ([03 › Trial & plans](03-business-tenancy.md#trial--plans)).

## Mail in production

Free hosts commonly block SMTP ports 25/465/587, so `MAIL_PORT` defaults to **2525** (supported by Brevo, Mailgun and SendGrid) and `MAIL_TIMEOUT=10` keeps a dead SMTP server from hanging a page load.

Even so, mail is treated as unreliable by design: `App\Support\SafeMail` catches the failure, the sign-up or invite still completes, and the operator can verify people by hand ([01](01-authentication.md#when-email-fails), [10 › Verifications](10-platform.md#email-verifications)).

## What's left

- A queue worker with `QUEUE_CONNECTION=database`, so email leaves the request cycle entirely (worth doing once mail is reliable).
- Automated database backups on a schedule (the host's managed backups cover this on paid plans).
- Error tracking (Sentry or similar) — today errors only reach the host's logs.
- Uptime monitoring of `/up`.
- The image has been built and reasoned through, but has **not** been run locally on this machine; it was validated by deploying it.
